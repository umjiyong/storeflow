# Problem Statement

## 1. 프로젝트 배경

StoreFlow는 오프라인 매장의 주문·결제 과정에서 발생할 수 있는 **중복 요청, 응답 유실, 데이터 정합성 문제와 장애 상황을 재현하고 해결하기 위한 서버 프로젝트**다.

오프라인 매장의 POS와 서버, 외부 결제 시스템 사이의 통신이 항상 안정적이라고 가정할 수는 없다.

결제 요청을 처리하는 과정에는 여러 시스템이 참여하며, 각 구간에서 네트워크 지연, 연결 종료, 프로세스 장애 등의 문제가 발생할 수 있다.

특히 결제에서는 단순히 요청이 성공했는지 실패했는지만으로 상태를 판단하기 어려운 상황이 존재한다.

대표적으로 다음 두 가지 상황을 구분할 필요가 있다.

### Case 1. 결제 결과는 확정되었지만 POS가 응답을 받지 못한 경우

```text
POS
 │
 │ 결제 요청
 ▼
StoreFlow
 │
 │ 승인 요청
 ▼
Payment Simulator
 │
 │ 승인 성공
 ▼
StoreFlow
 │
 │ Payment APPROVED 저장
 │
 X  POS로 응답 전달 실패
 │
POS
 │
 │ 동일 결제 재요청
 ▼
StoreFlow
```

StoreFlow는 이미 결제가 승인되었다는 사실을 알고 있지만 POS는 결과를 받지 못했다.

POS가 동일한 결제를 다시 요청했을 때 이를 새로운 결제로 처리하면 중복 승인이 발생할 수 있다.

따라서 동일한 논리적 결제 요청이 다시 전달되더라도 **기존 처리 결과를 식별하고 동일한 결과를 반환할 수 있어야 한다.**

### Case 2. 외부 결제 시스템의 승인 결과 자체를 알 수 없는 경우

```text
StoreFlow
 │
 │ 승인 요청
 ▼
Payment Simulator
 │
 │ 승인 성공
 │
 X  승인 응답 유실
 │
StoreFlow
```

외부 결제 시스템에서는 실제 승인이 완료되었지만 StoreFlow가 응답을 받지 못할 수도 있다.

이 경우 StoreFlow는 실제 결제가 성공했는지 실패했는지를 즉시 판단할 수 없다.

이를 단순 실패로 처리하고 다시 승인 요청을 수행하면 중복 결제가 발생할 수 있고, 반대로 성공으로 간주하면 실제로는 승인되지 않은 결제를 완료 상태로 처리할 수 있다.

따라서 StoreFlow에서는 정상적인 주문·결제 기능 구현 자체보다 **실패가 발생했을 때도 결제 상태를 추적하고, 중복 처리를 방지하며, 불확실한 상태를 명시적으로 관리하고, 최종적으로 신뢰할 수 있는 상태로 복구할 수 있는 구조**를 만드는 것을 핵심 문제로 정의한다.

또한 결제 완료 이후 주문, 정산 등 다른 기능으로 상태 변화가 전달되는 과정에서도 일부 시스템만 상태 변경에 성공하는 문제가 발생할 수 있다.

StoreFlow는 이러한 문제를 코드로 예방한다고 가정하지 않고 **실패 상황을 직접 재현하고 테스트와 지표를 통해 검증하는 것**을 프로젝트의 기본 접근 방식으로 삼는다.

---

## 2. 해결하려는 핵심 문제

StoreFlow에서는 다음 네 가지 문제를 핵심적으로 다룬다.

### 2.1 중복 결제

POS는 네트워크 지연이나 응답 유실로 인해 동일한 결제 요청을 다시 전송할 수 있다.

또한 사용자의 반복 입력이나 클라이언트 재시도에 의해 동일한 논리적 요청이 거의 동시에 여러 번 전달될 수도 있다.

서버가 각각의 요청을 독립적인 결제로 판단한다면 하나의 주문에 대해 외부 결제 승인이 여러 번 수행될 수 있다.

따라서 다음 조건을 만족해야 한다.

> 동일한 논리적 결제 요청이 반복되거나 동시에 전달되더라도 실제 결제 승인은 한 번만 수행되어야 한다.

또한 동일한 요청을 다시 전달한 경우에는 기존 처리 결과를 식별하여 일관된 응답을 반환할 수 있어야 한다.

---

### 2.2 결제 결과의 불확실성

외부 결제 시스템에 승인 요청을 전달한 이후 연결이 종료되면 StoreFlow가 승인 결과를 확인하지 못할 수 있다.

```text
StoreFlow → Payment Simulator : 승인 요청

Payment Simulator : 승인 성공

Payment Simulator → StoreFlow : 응답 전송 실패
```

이 상황에서는 단순히 결제를 `FAILED`로 처리할 수 없다.

외부 시스템에서는 이미 승인이 완료되었을 가능성이 있기 때문이다.

반대로 성공했다고 가정할 수도 없다.

따라서 **성공과 실패를 즉시 결정할 수 없는 상태를 시스템에서 명시적으로 표현하고, 이후 조회 또는 복구 절차를 통해 최종 상태를 결정할 수 있어야 한다.**

프로젝트에서는 이러한 상태를 `UNKNOWN`으로 표현하고 다음과 같은 질문을 검증한다.

* 어떤 실패 지점에서 `UNKNOWN` 상태가 발생할 수 있는가?
* `UNKNOWN` 상태에서 동일 결제 요청이 다시 들어오면 어떻게 처리해야 하는가?
* 외부 결제 시스템의 실제 상태를 어떻게 확인할 것인가?
* 일정 시간 동안 상태를 확정할 수 없다면 어떤 방식으로 관리할 것인가?
* 복구 과정 자체가 중복 실행되더라도 안전한가?

---

### 2.3 데이터 저장과 이벤트 전달 사이의 불일치

결제 완료 이후 주문, 정산 등 다른 기능에서 결제 결과를 사용해야 할 수 있다.

```text
Payment APPROVED
        │
        └── Event
              │
              ├── Order
              └── Settlement
```

하지만 데이터베이스 상태 변경과 메시지 브로커를 통한 이벤트 발행은 서로 다른 시스템에서 수행된다.

따라서 다음과 같은 상황이 발생할 수 있다.

```text
Payment DB 저장 성공
        ↓
Event 발행 실패
```

이 경우 결제 시스템에서는 승인된 결제로 기록되어 있지만 후속 기능에서는 결제 완료 사실을 알지 못한다.

반대로 이벤트가 전달된 이후 동일 이벤트가 다시 전달되는 상황도 고려해야 한다.

StoreFlow에서는 다음 문제를 검증한다.

* 결제 상태 변경과 이벤트 생성 사이의 불일치를 어떻게 방지할 것인가?
* 메시지 브로커가 중단된 동안 발생한 이벤트를 어떻게 보존할 것인가?
* 복구 후 동일 이벤트가 여러 번 전달되어도 후속 처리가 중복 반영되지 않는가?
* 이벤트 전달 성공 여부와 비즈니스 처리 성공 여부가 서로 어긋나지 않는가?

프로젝트에서는 이벤트를 정확히 한 번 전달한다고 가정하지 않는다.

메시지가 중복 전달될 수 있다는 조건에서 **데이터 유실을 방지하고 Consumer가 중복 처리에도 안전하게 동작하는 구조**를 검증한다.

---

### 2.4 장애의 전파와 복구

StoreFlow가 의존하는 외부 결제 시스템, 데이터베이스, Kafka와 같은 구성 요소는 언제든 지연되거나 사용할 수 없는 상태가 될 수 있다.

프로젝트 진행 과정에서 Redis가 특정 문제를 해결하기 위해 도입되는 경우 Redis 장애 역시 검증 대상에 포함한다.

하나의 구성 요소에서 발생한 장애가 다른 기능까지 무제한으로 전파되어서는 안 된다.

예를 들어 외부 결제 시스템의 응답이 장시간 지연되는 상황에서 결제 요청이 데이터베이스 Connection을 계속 점유한다면 결제와 무관한 주문 조회까지 실패할 수 있다.

또한 장애가 해소된 이후에는 단순히 시스템이 다시 실행되는 것만으로 충분하지 않다.

장애 동안 처리되지 못한 데이터가 남아 있다면 이를 안전하게 다시 처리하여 정상 상태로 수렴할 수 있어야 한다.

따라서 StoreFlow에서는 다음 흐름을 함께 검증한다.

```text
장애 발생
→ 사용자 영향 확인
→ 시스템 상태 관측
→ 장애 전파 범위 확인
→ 복구
→ 미처리 데이터 재처리
→ 정상 상태 수렴 확인
```

정상 흐름뿐 아니라 **장애가 발생했을 때 시스템이 어떤 상태를 유지하고, 장애가 해소된 이후 어떻게 정상 상태로 돌아오는지**를 프로젝트의 주요 검증 대상으로 삼는다.

# 핵심 위험–검증 방법 매핑표

각 설계가 안전하다고 가정하지 않고 테스트와 장애 실험을 통해 실제 동작을 검증한다.

구체적인 해결 방법은 초기 단계에서 정답으로 고정하지 않는다.

먼저 위험을 재현한 뒤 여러 해결 방법을 비교하고, 실제 선택한 방식과 트레이드오프는 ADR에 기록한다.

| 핵심 위험                 | 발생 가능한 문제                   | 검증 방법                             | 성공 기준                            | 검증 시점 |
| --------------------- | --------------------------- | --------------------------------- | -------------------------------- | ----- |
| 동일 결제 재요청             | 동일 주문이 여러 번 승인됨             | 동일 `Idempotency-Key`로 요청 반복       | 외부 결제 승인이 1회만 발생하고 동일 결과 반환      | 1개월 차 |
| 동일 결제 동시 요청           | Race Condition으로 중복 승인      | 동일 논리 요청을 10개 이상 동시에 실행           | 하나의 결제만 실제 승인됨                   | 1개월 차 |
| 멱등성 키 오사용             | 서로 다른 요청이 동일 결제로 처리됨        | 같은 키에 서로 다른 요청 Body 전송            | 요청을 거부하고 기존 결제 결과를 변경하지 않음       | 1개월 차 |
| StoreFlow → POS 응답 유실 | POS 재시도로 중복 승인 가능           | 승인 완료 후 클라이언트 응답 전달 실패 재현         | 재요청 시 외부 승인 없이 기존 결과 반환          | 1개월 차 |
| PG 승인 결과 유실           | 실제 승인 여부를 알 수 없음            | 승인 완료 후 PG 응답 연결 종료               | `FAILED`로 단정하지 않고 `UNKNOWN`으로 관리 | 1개월 차 |
| 결제 처리 중 서버 종료         | `PROCESSING` 상태 고착 또는 중복 승인 | 결제 단계별 애플리케이션 강제 종료               | 재요청·복구 후 데이터가 정의된 상태로 수렴         | 1개월 차 |
| DB 저장과 이벤트 발행 불일치     | 결제 완료 사실이 후속 시스템에 전달되지 않음   | DB Commit과 이벤트 발행 사이에 장애 발생       | 이벤트가 유실되지 않고 복구 후 전달됨            | 1개월 차 |
| 이벤트 중복 전달             | 동일 주문·정산 결과가 여러 번 반영됨       | 동일 `eventId` 반복 전달                | Consumer 결과가 한 번만 반영됨            | 1개월 차 |
| Consumer 처리 중 종료      | 비즈니스 처리와 Offset 상태 불일치      | 이벤트 처리 단계에서 Consumer 종료           | 재전달되어도 비즈니스 결과가 중복 반영되지 않음       | 1개월 차 |
| Kafka 장시간 중단          | 발행되지 못한 이벤트 지속 적체           | Kafka를 일정 시간 중단                   | 핵심 결제 상태는 보존되고 복구 후 이벤트 전달       | 1개월 차 |
| Kafka 복구 후 이벤트 급증     | Consumer 및 DB 순간 부하 증가      | 이벤트를 적체한 뒤 Kafka 복구               | 데이터 유실 없이 처리되고 시스템이 정상 상태로 수렴    | 2개월 차 |
| 외부 결제 시스템 응답 지연       | 요청과 Connection이 누적되어 장애 전파  | Payment Simulator 응답 시간을 의도적으로 증가 | 장애 영향과 병목을 지표로 식별 가능             | 1개월 차 |
| DB Connection Pool 고갈 | 결제 외 API까지 응답 지연 또는 실패      | Connection Pool 제한 후 부하 발생        | 원인을 지표로 탐지하고 개선 전후 비교 가능         | 1개월 차 |
| Redis 장애              | Redis 의존 기능이 정지하거나 정합성 손상   | Redis 도입 후 실행 중 강제 중단             | 핵심 영속 데이터의 정합성이 Redis에만 의존하지 않음  | 도입 이후 |
| 재고 동시 차감              | 재고가 음수가 되거나 초과 판매 발생        | 재고 1개에 다수 주문 동시 실행                | 성공 주문 수가 실제 재고를 초과하지 않음          | 2개월 차 |
| 재고 예약 후 결제 실패         | 실제 판매되지 않은 상품이 계속 점유됨       | 재고 예약 후 결제 실패 재현                  | 정의된 정책에 따라 재고가 안전하게 복원됨          | 2개월 차 |
| 주문 만료 처리 중복           | 동일 재고가 여러 번 복원됨             | 동일 만료 처리를 반복 실행                   | 재고 수량이 최초 값 이상으로 증가하지 않음         | 2개월 차 |
| 취소 요청 중복              | 같은 결제가 여러 번 취소됨             | 동일 취소 요청 반복·동시 실행                 | 허용된 취소 금액만 한 번 반영됨               | 2개월 차 |
| 취소 이벤트 중복 전달          | 원장에 동일 차감이 여러 번 기록됨         | 동일 취소 이벤트 반복 전달                   | 동일 이벤트가 원장에 한 번만 반영됨             | 2개월 차 |
| 정산 중복 처리              | 매출 또는 환불 금액이 중복 집계됨         | 동일 이벤트를 정산 시스템에 반복 전달             | 동일 이벤트가 정산 결과에 한 번만 반영됨          | 2개월 차 |
| 정산 Consumer 처리 중 종료   | 정산 반영 후 메시지가 재전달됨           | 처리 중 Consumer 또는 Pod 종료           | 재전달 이후에도 정산 금액이 변하지 않음           | 2개월 차 |

> 검증 항목은 프로젝트 진행 과정에서 실제로 발견한 새로운 실패 가능성에 따라 추가한다.
> 검증하지 않은 동작을 시스템이 보장한다고 표현하지 않는다.

---

# 프로젝트에서 하지 않을 것

StoreFlow의 목적은 실제 상용 결제 서비스를 완전히 구현하는 것이 아니다.

제한된 기간 동안 핵심 서버 설계와 신뢰성 문제를 깊게 검증하기 위해 다음 영역은 프로젝트 범위에서 제외한다.

## 1. 실제 금융 결제 연동

다음 시스템과 실제로 연동하지 않는다.

* 실제 카드사
* VAN
* PG
* 은행 및 금융기관
* 실제 결제 단말기

POS 역할과 외부 결제 시스템은 프로젝트에서 필요한 범위만 시뮬레이션한다.

외부 결제 시스템은 별도의 `Payment Simulator`를 통해 다음 상태를 제어할 수 있도록 구성한다.

* 승인 성공
* 승인 실패
* 응답 지연
* 승인 후 응답 유실
* 서버 오류

이를 통해 실제 금융 시스템과 연결하지 않고도 StoreFlow에서 검증하려는 장애 상황을 재현한다.

---

## 2. 실제 금융 서비스 수준의 보안·규제 구현

다음 영역을 상용 금융 서비스 수준으로 구현하거나 준수했다고 주장하지 않는다.

* 실제 카드 정보 저장 및 처리
* PCI DSS 인증
* 금융 관련 법규 및 규제 준수
* 실제 가맹점 인증
* 실거래 데이터 처리
* 운영 환경의 보안 인증

프로젝트에서는 테스트 데이터만 사용하며 실제 카드 정보나 금융 정보를 저장하지 않는다.

보안 관련 기본적인 개발 원칙을 적용하는 것과 실제 금융 서비스 수준의 보안·규제를 검증하는 것은 구분한다.

---

## 3. 실제 서비스 규모의 트래픽을 재현했다고 주장하지 않는다

부하 테스트는 시스템의 절대적인 처리 성능이나 실제 상용 서비스의 처리 용량을 증명하기 위한 것이 아니다.

다음 목적으로 사용한다.

* 병목 발견
* 설계 변경 전후 비교
* 장애 상황에서 시스템 변화 관측
* 처리량 증가에 따른 자원 사용 변화 확인
* 특정 설계 선택의 성능상 트레이드오프 확인

개인 개발 환경에서 측정한 TPS, P95/P99 응답 시간 등의 수치를 실제 상용 결제 서비스 규모의 성능으로 일반화하지 않는다.

성능 테스트 결과에는 반드시 다음 정보를 함께 기록한다.

* 테스트 환경
* 요청 시나리오
* 동시 사용자 수
* 테스트 지속 시간
* 애플리케이션 자원 제한
* 외부 시스템 Simulator 조건

---

## 4. 처음부터 MSA로 구성하지 않는다

서비스 개수를 늘리는 것 자체를 목표로 하지 않는다.

초기에는 Modular Monolith 구조에서 비즈니스 규칙과 트랜잭션 경계를 명확하게 정의한다.

서비스 분리는 다음과 같은 필요성이 확인될 때 수행한다.

* 독립적인 확장이 필요한가?
* 장애를 격리할 필요가 있는가?
* 데이터 소유권을 명확하게 분리할 수 있는가?
* 독립적인 배포가 구조적으로 의미가 있는가?
* 분리에 따라 증가하는 운영 복잡성을 감수할 가치가 있는가?

프로젝트 후반에는 이러한 기준을 바탕으로 하나 이상의 서비스를 실제로 분리하고, 분리 이전과 이후의 비용과 효과를 비교한다.

서비스 분리 자체를 아키텍처 발전의 성공 기준으로 사용하지 않는다.

---

## 5. 기술 스택을 채우기 위한 기술 도입을 하지 않는다

특정 기술을 사용했다는 경험을 만들기 위해 기술을 추가하지 않는다.

기술 도입은 다음 순서로 결정한다.

```text
문제 정의
→ 현재 구조에서 문제 재현
→ 해결 방법 후보 비교
→ 기술 도입 필요성 판단
→ 구현
→ 테스트
→ 결과 측정
→ 판단 기록
```

따라서 프로젝트 계획에 포함된 기술이라도 실제 문제 해결에 필요하지 않다고 판단되면 사용하지 않거나 범위를 축소할 수 있다.

반대로 기술을 도입했다면 다음 질문에 답할 수 있어야 한다.

* 어떤 문제를 해결하기 위해 도입했는가?
* 기존 방식으로는 해결할 수 없었는가?
* 다른 대안은 무엇이었는가?
* 해당 기술이 추가한 복잡성은 무엇인가?
* 해당 기술이 장애를 일으키면 시스템은 어떻게 동작하는가?

---

## 6. 1개월 차에는 인프라 범위를 확장하지 않는다

첫 번째 달에는 결제 신뢰성, 데이터 정합성, 장애 처리와 테스트에 집중한다.

따라서 다음 영역은 1개월 차 범위에서 제외한다.

* Kubernetes
* Istio
* ArgoCD / GoCD
* Elasticsearch
* MongoDB
* Spring Cloud 기반 MSA
* 복잡한 Frontend

첫 달에는 Docker Compose를 이용해 재현 가능한 개발·테스트 환경을 구성한다.

Kubernetes와 서비스 분리는 핵심 결제 구조와 이벤트 정합성이 검증된 이후 두 번째 달에 진행한다.

2개월 차에도 프로젝트의 핵심 검증 일정을 방해한다면 ArgoCD와 같은 후순위 인프라 작업은 축소할 수 있다.

---

## 7. 주변 비즈니스 기능을 확장하지 않는다

다음 기능은 핵심 목표와 직접적인 관련이 없으므로 구현하지 않는다.

* 회원 시스템
* 포인트
* 쿠폰
* 배달
* 예약
* 리뷰
* 마케팅
* 추천 시스템
* 복잡한 관리자 화면

프로젝트의 제품 범위는 다음 흐름을 중심으로 제한한다.

```text
Store
→ Product
→ Inventory
→ Order
→ Payment
→ Refund
→ Settlement
```

새로운 기능이 필요해 보이는 경우에도 해당 기능이 핵심 위험 검증에 필요한지 먼저 판단한다.

---

## 8. 실제 운영 경험으로 포장하지 않는다

프로젝트에서 의도적으로 발생시킨 장애는 실제 운영 장애가 아니라 **장애 실험(Failure Injection)** 으로 명확하게 구분한다.

부하 테스트 역시 실제 사용자 트래픽이 아닌 통제된 테스트 환경에서 생성된 트래픽이다.

따라서 프로젝트 결과를 다음과 같이 표현하지 않는다.

> 대규모 결제 서비스를 운영하며 장애를 해결했다.

> 실제 결제 트래픽을 안정적으로 처리했다.

> 고가용성 결제 시스템을 운영했다.

대신 실제 수행한 범위에 맞게 표현한다.

> 오프라인 결제 시스템에서 발생할 수 있는 중복 요청, 응답 유실, 이벤트 불일치 등의 장애 시나리오를 정의하고 직접 재현하여 설계와 복구 전략을 검증했다.

또한 부하 테스트나 장애 실험의 결과를 제시할 때는 테스트 조건과 검증 범위를 함께 기록한다.

---

## 9. 검증하지 않은 특성을 보장한다고 표현하지 않는다

설계 패턴이나 기술을 적용했다는 사실만으로 시스템 특성이 보장된다고 가정하지 않는다.

예를 들어 다음과 같은 표현은 실제 검증 이후에만 사용한다.

* 중복 결제를 방지한다.
* 이벤트를 유실하지 않는다.
* 장애가 다른 기능으로 전파되지 않는다.
* 고가용성을 보장한다.
* 확장 가능한 구조다.
* 높은 트래픽을 안정적으로 처리한다.

구현 이전에는 이를 **목표 또는 가설**로 표현하고, 구현 이후에는 테스트와 지표를 근거로 검증된 범위만 기록한다.

---

# 프로젝트 검증 원칙

StoreFlow에서는 구현 여부와 검증 여부를 구분한다.

기능이 정상적으로 실행된다는 사실만으로 해당 기능이 완료되었다고 판단하지 않는다.

각 핵심 문제는 가능한 한 다음 과정으로 검증한다.

```text
문제 정의
→ 실패 조건 정의
→ 가장 단순한 구현
→ 실패 재현
→ 원인 분석
→ 해결 방법 후보 비교
→ 개선
→ 동일 조건 재검증
→ 결과 기록
```

특히 성능 개선에서는 여러 변경을 동시에 적용하지 않는다.

한 번에 하나의 가설과 하나의 개선을 적용하고 동일한 조건에서 변경 전후를 비교한다.

설계 판단은 가능하면 다음 네 가지 증거가 동일한 내용을 설명하도록 유지한다.

```text
Code
Test
Metric
Document
```

코드가 의도한 동작은 테스트로 검증하고, 운영 특성은 지표로 관측하며, 선택 이유와 한계는 문서로 기록한다.

---

# 문제 정의 요약

StoreFlow가 해결하고자 하는 문제는 기능의 개수가 아니라 **실패 상황에서도 주문과 결제에 관련된 핵심 데이터가 신뢰할 수 있는 상태로 수렴하도록 만드는 것**이다.

프로젝트에서는 다음 질문에 코드, 테스트, 지표, 문서로 답하는 것을 목표로 한다.

> 동일한 결제 요청이 반복되거나 동시에 전달되어도 중복 결제를 방지할 수 있는가?

> StoreFlow는 결제 결과를 알고 있지만 POS가 결과를 받지 못한 경우, 재요청에 안전하게 기존 결과를 반환할 수 있는가?

> 외부 결제 시스템의 응답을 받지 못해 실제 승인 여부를 모르는 상태를 안전하게 표현하고 복구할 수 있는가?

> 데이터베이스 상태 변경과 이벤트 전달 사이의 불일치를 어떻게 처리할 것인가?

> 이벤트가 중복 전달되거나 Consumer가 처리 도중 종료되어도 비즈니스 결과가 중복 반영되지 않는가?

> 외부 결제 시스템, Kafka, 데이터베이스 또는 애플리케이션 자체가 실패했을 때 장애가 어떤 범위까지 전파되는가?

> 장애가 해소된 이후 미처리 데이터를 안전하게 다시 처리하여 정상 상태로 수렴할 수 있는가?

> 시스템이 안전하다는 판단을 구현 코드가 아니라 테스트와 관측 결과로 증명할 수 있는가?

프로젝트 진행 과정에서 이 질문에 대한 답을 지속적으로 검증하고, 검증 결과에 따라 설계와 문서를 함께 갱신한다.
