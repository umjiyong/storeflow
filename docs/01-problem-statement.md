# Problem Statement

## 1. 프로젝트 배경

StoreFlow는 오프라인 매장의 주문·결제 과정에서 발생할 수 있는 **중복 요청, 응답 유실, 데이터 정합성 문제와 장애 상황을 재현하고 해결하기 위한 서버 프로젝트**다.

오프라인 매장의 POS는 항상 안정적인 네트워크 환경에서 동작한다고 가정할 수 없다.

결제 요청을 처리하는 과정에는 POS, StoreFlow 서버, 외부 결제 시스템 등 여러 주체가 참여하며, 각 구간에서 네트워크 지연이나 연결 종료, 서버 장애가 발생할 수 있다.

예를 들어 외부 결제 시스템에서는 승인이 완료되었지만 POS가 결과를 전달받지 못한다면 사용자는 결제가 실패했다고 판단하여 동일한 결제를 다시 요청할 수 있다.

```text
POS
 │
 │ 결제 요청
 ▼
StoreFlow
 │
 │ 승인 요청
 ▼
Payment System
 │
 │ 승인 성공
 ▼
StoreFlow
 │
 X  응답 유실
 │
POS
 │
 │ 동일 결제 재요청
 ▼
StoreFlow
```

이때 단순히 새로운 요청으로 처리하면 동일한 주문에 대해 결제가 중복으로 승인될 수 있다.

또한 결제 결과가 데이터베이스에 정상적으로 저장되더라도 후속 시스템에 전달하기 위한 이벤트 발행이 실패하면 시스템마다 서로 다른 결제 상태를 가지게 될 수 있다.

따라서 StoreFlow에서는 정상적인 결제 기능 구현 자체보다 **실패가 발생하더라도 결제 상태를 추적하고, 중복 처리를 방지하며, 시스템이 일관된 상태로 복구될 수 있는 구조**를 만드는 것을 핵심 문제로 정의한다.

---

## 2. 해결하려는 핵심 문제

StoreFlow에서는 다음 네 가지 문제를 핵심적으로 다룬다.

### 2.1 중복 결제

POS가 결제 결과를 전달받지 못하면 동일한 결제 요청을 다시 전송할 수 있다.

서버가 각각의 요청을 독립적인 결제로 판단한다면 실제로는 하나의 주문임에도 외부 결제 승인이 여러 번 발생할 수 있다.

따라서 동일한 논리적 결제 요청이 반복되거나 동시에 전달되더라도 **실제 결제 승인은 한 번만 수행되어야 한다.**

---

### 2.2 결제 결과의 불확실성

외부 결제 시스템에 요청을 전달한 이후 연결이 종료되면 StoreFlow가 승인 결과를 확인하지 못할 수 있다.

```text
StoreFlow → Payment System : 승인 요청

Payment System : 승인 성공

Payment System → StoreFlow : 응답 전송 실패
```

이 상황에서는 단순히 결제를 `FAILED`로 처리할 수 없다.

외부 시스템에서는 이미 승인이 완료되었을 가능성이 있기 때문이다.

따라서 **성공과 실패를 즉시 결정할 수 없는 상태를 시스템에서 명시적으로 표현하고 이후 실제 결과를 확인하여 복구할 수 있어야 한다.**

---

### 2.3 데이터 저장과 이벤트 전달 사이의 불일치

결제 완료 이후 주문, 정산 등 다른 기능에서 결제 결과를 사용해야 할 수 있다.

```text
Payment APPROVED
        │
        └── Event
              │
              ├── Order
              └── Settlement
```

하지만 데이터베이스 저장과 이벤트 발행은 서로 다른 시스템에서 수행되기 때문에 다음과 같은 문제가 발생할 수 있다.

```text
Payment DB 저장 성공
        ↓
Kafka 이벤트 발행 실패
```

이 경우 결제 시스템에서는 승인된 결제로 기록되어 있지만 후속 시스템에서는 해당 사실을 알 수 없다.

따라서 **결제 상태 변경과 후속 이벤트 전달 사이에서 발생할 수 있는 불일치를 탐지하고 복구할 수 있어야 한다.**

---

### 2.4 장애의 전파와 복구

외부 결제 시스템, Kafka, Redis, 데이터베이스 등 StoreFlow가 의존하는 구성 요소는 언제든 지연되거나 사용할 수 없는 상태가 될 수 있다.

하나의 구성 요소에서 발생한 장애가 전체 서비스의 장애로 확대되지 않도록 해야 하며, 장애가 해소된 이후에는 처리되지 못한 작업을 안전하게 복구할 수 있어야 한다.

따라서 정상 흐름뿐 아니라 **장애가 발생했을 때 시스템이 어떤 상태를 유지하고 어떻게 정상 상태로 돌아오는지**를 프로젝트의 주요 검증 대상으로 삼는다.

---

# 핵심 위험–검증 방법 매핑표

각 설계가 안전하다고 가정하지 않고 테스트와 장애 실험을 통해 실제 동작을 검증한다.

| 핵심 위험                 | 발생 가능한 문제                          | 검증 방법                       | 성공 기준                           |
| --------------------- | ---------------------------------- | --------------------------- | ------------------------------- |
| 동일 결제 재요청             | 동일 주문이 여러 번 승인됨                    | 동일 `Idempotency-Key`로 요청 반복 | 외부 결제 승인이 1회만 발생                |
| 동일 결제 동시 요청           | Race Condition으로 중복 승인             | 동일 키로 10개 이상의 요청 동시 실행      | 하나의 요청만 실제 승인을 수행               |
| 멱등성 키 오사용             | 서로 다른 결제가 동일 요청으로 처리됨              | 같은 키에 서로 다른 요청 Body 전송      | 요청을 거부하고 기존 결제 상태 유지            |
| PG 승인 후 응답 유실         | 실제 승인 여부를 모르는 상태 발생                | 승인 후 연결을 의도적으로 종료           | `FAILED`로 단정하지 않고 불확실 상태로 관리    |
| 결제 처리 중 서버 종료         | 처리 중 상태가 영구적으로 남거나 중복 승인 발생        | 결제 처리 단계별 프로세스 강제 종료        | 재요청 또는 복구 과정에서 안전한 상태로 수렴       |
| DB 저장 후 Kafka 발행 실패   | 결제는 완료됐지만 후속 시스템이 알지 못함            | DB Commit 이후 Kafka 중단       | 이벤트가 유실되지 않고 복구 후 전달            |
| Kafka 이벤트 중복 전달       | 주문·정산 등이 여러 번 반영됨                  | 동일 `eventId` 이벤트 반복 전달      | Consumer 결과가 한 번만 반영            |
| Consumer 처리 중 종료      | 처리 결과와 Offset 상태가 불일치              | 이벤트 처리 도중 Consumer 종료       | 재전달 이후에도 결과가 중복 반영되지 않음         |
| Kafka 장시간 중단          | Outbox 이벤트 지속 적체                   | Kafka를 일정 시간 중단             | 결제 자체는 보존되고 복구 후 이벤트 전달         |
| Kafka 복구 후 이벤트 급증     | Consumer 및 DB 순간 부하 증가             | Outbox를 적체한 뒤 Kafka 복구      | 데이터 유실 없이 처리되며 시스템 상태가 정상으로 수렴  |
| Redis 장애              | 멱등성 또는 핵심 결제 기능 상실                 | 결제 처리 중 Redis 중단            | 핵심 결제 데이터의 정합성이 Redis에만 의존하지 않음 |
| PG 응답 지연              | 요청·Connection이 누적되어 다른 API까지 장애 전파 | PG 응답 시간을 의도적으로 증가          | 장애 영향을 관측하고 병목 및 전파 범위를 확인      |
| DB Connection Pool 고갈 | 전체 API 응답 지연 또는 실패                 | Connection Pool을 제한하고 부하 발생 | 원인을 지표로 탐지하고 개선 전후를 비교          |
| 재고 동시 차감              | 재고가 음수가 되거나 초과 판매 발생               | 재고 1개에 다수 주문 동시 실행          | 성공 주문 수가 실제 재고를 초과하지 않음         |
| 취소 이벤트 중복 처리          | 동일 금액이 여러 번 환불·차감됨                 | 동일 취소 요청 및 이벤트 반복           | 한 번의 취소만 원장에 반영                 |
| 정산 중복 처리              | 매출 또는 환불 금액이 중복 집계됨                | 동일 이벤트를 정산 시스템에 반복 전달       | 동일 이벤트가 정산 결과에 한 번만 반영          |

> 검증 항목은 프로젝트 진행 과정에서 실제로 발견한 새로운 실패 가능성에 따라 추가한다.
> 검증하지 않은 동작을 시스템이 보장한다고 표현하지 않는다.

# 프로젝트에서 하지 않을 것

StoreFlow의 목적은 실제 상용 결제 서비스를 완전히 구현하는 것이 아니다.

제한된 기간 동안 핵심 서버 설계와 신뢰성 문제를 깊게 검증하기 위해 다음 영역은 프로젝트 범위에서 제외한다.

## 1. 실제 금융 결제 연동

다음 시스템과 실제로 연동하지 않는다.

* 실제 카드사
* VAN
* PG
* 은행 및 금융기관
* 실제 결제 단말기

외부 결제 시스템은 프로젝트 내부의 `Payment Simulator`를 통해 필요한 성공·실패·지연·응답 유실 상황을 재현한다.

---

## 2. 실제 금융 서비스 수준의 보안·규제 구현

다음 영역을 상용 금융 서비스 수준으로 구현하거나 준수했다고 주장하지 않는다.

* 실제 카드 정보 저장 및 처리
* PCI DSS 인증
* 금융 관련 법규 및 규제 준수
* 실제 가맹점 인증
* 실거래 데이터 처리
* 운영 환경의 보안 인증

테스트 데이터만 사용하며 실제 카드 정보나 금융 정보를 저장하지 않는다.

---

## 3. 실제 서비스 규모의 트래픽을 재현했다고 주장하지 않는다

부하 테스트는 시스템의 절대적인 처리 성능을 증명하기 위한 것이 아니다.

다음 목적으로 사용한다.

* 병목 발견
* 설계 변경 전후 비교
* 장애 상황에서 시스템 변화 관측
* 처리량 증가에 따른 자원 사용 변화 확인

개인 개발 환경에서 측정한 TPS나 응답 시간을 실제 상용 결제 서비스 규모의 성능으로 일반화하지 않는다.

---

## 4. 처음부터 MSA로 구성하지 않는다

서비스 개수를 늘리는 것 자체를 목표로 하지 않는다.

초기에는 Modular Monolith 구조에서 비즈니스 규칙과 트랜잭션 경계를 명확하게 정의한다.

서비스 분리는 다음과 같은 필요성이 확인될 때 수행한다.

* 독립적인 확장이 필요한 경우
* 장애 격리가 필요한 경우
* 데이터 소유권이 명확하게 분리되는 경우
* 독립적인 배포가 구조적으로 의미가 있는 경우

프로젝트 후반에는 이러한 기준을 바탕으로 하나 이상의 서비스를 실제로 분리하고 그 비용과 효과를 비교한다.

---

## 5. 기술 스택을 채우기 위한 기술 도입을 하지 않는다

특정 기술을 사용했다는 경험을 만들기 위해 기술을 추가하지 않는다.

다음 순서로 기술 도입을 결정한다.

```text
문제 정의
→ 현재 구조에서 재현
→ 해결 방법 후보 비교
→ 기술 도입 필요성 판단
→ 구현
→ 테스트
→ 결과 측정
```

따라서 계획에 포함된 기술도 실제 문제 해결에 필요하지 않다고 판단되면 사용하지 않을 수 있다.

---

## 6. 1개월 차에는 인프라 범위를 확장하지 않는다

첫 번째 달에는 결제 신뢰성과 메시지 정합성에 집중하기 위해 다음 기술을 제외한다.

* Kubernetes
* Istio
* ArgoCD / GoCD
* Elasticsearch
* MongoDB
* Spring Cloud 기반 MSA
* 복잡한 Frontend

해당 기간에는 Docker Compose 기반으로 재현 가능한 개발·테스트 환경을 구성한다.

Kubernetes와 서비스 분리는 핵심 결제 구조가 검증된 이후 두 번째 달에 진행한다.

---

## 7. 주변 비즈니스 기능을 확장하지 않는다

다음 기능은 핵심 목표와 직접적인 관련이 없으므로 구현하지 않는다.

* 회원 시스템
* 포인트
* 쿠폰
* 배달
* 예약
* 리뷰
* 마케팅
* 추천 시스템
* 복잡한 관리자 화면

프로젝트의 제품 범위는 다음 흐름을 중심으로 제한한다.

```text
Store
→ Product
→ Inventory
→ Order
→ Payment
→ Refund
→ Settlement
```

---

## 8. 실제 운영 경험으로 포장하지 않는다

의도적으로 발생시킨 장애는 **장애 실험(Failure Injection)** 으로 명확하게 구분한다.

부하 테스트 역시 실제 사용자 트래픽이 아닌 통제된 테스트 환경의 결과로 기록한다.

따라서 프로젝트 결과를 다음과 같이 표현하지 않는다.

> 대규모 결제 서비스를 운영하며 장애를 해결했다.

대신 실제 수행한 범위에 맞게 표현한다.

> 결제 시스템에서 발생할 수 있는 중복 요청과 응답 유실, 이벤트 불일치 등의 장애 시나리오를 정의하고 직접 재현하여 설계와 복구 전략을 검증했다.

---

# 문제 정의 요약

StoreFlow가 해결하고자 하는 문제는 기능의 개수가 아니라 **실패 상황에서도 결제와 관련된 핵심 데이터가 신뢰할 수 있는 상태로 수렴하도록 만드는 것**이다.

프로젝트에서는 다음 질문에 코드, 테스트, 지표, 문서로 답하는 것을 목표로 한다.

> 동일한 결제 요청이 반복되거나 동시에 전달되어도 중복 결제를 방지할 수 있는가?

> 외부 시스템의 응답을 받지 못했을 때 실제 결제 결과를 모르는 상태를 안전하게 표현하고 복구할 수 있는가?

> 데이터베이스 상태 변경과 이벤트 전달 사이의 불일치를 어떻게 처리할 것인가?
