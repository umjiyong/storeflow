# Business Rules

## 문서 목적

이 문서는 StoreFlow의 주문·결제 과정에서 지켜야 할 **비즈니스 규칙**, 해당 규칙이 적용되는 **정상·예외 사용자 시나리오**, 시스템이 반드시 보장해야 할 **주요 불변식(Invariant)** 을 정의한다.

구체적인 도메인 모델, 상태 구조, 트랜잭션 경계, 동시성 제어 방식 등의 구현 방법은 이 문서에서 결정하지 않는다.

이 문서에서 정의한 규칙과 시나리오는 이후 도메인 모델링과 테스트의 기준으로 사용한다.

---

# 1. 비즈니스 규칙

## BR-01. 결제가 완료된 주문은 다시 결제할 수 없다

하나의 주문에 대한 결제가 이미 완료되었다면 동일한 주문에 새로운 결제 승인을 수행해서는 안 된다.

POS가 결제 결과를 전달받지 못해 동일한 주문에 대해 다시 결제를 요청하는 경우에도 새로운 결제를 수행하지 않고 기존 결제 결과를 확인하여 응답해야 한다.

```text
Order A
→ Payment APPROVED

Order A
→ 결제 재요청

새로운 결제 승인 X
```

---

## BR-02. 같은 멱등성 키와 같은 요청은 같은 결과를 반환한다

동일한 `Idempotency-Key`와 동일한 요청 내용이 다시 전달되었다면 새로운 요청으로 처리하지 않는다.

최초 요청이 이미 완료된 경우 기존 처리 결과를 반환해야 한다.

```text
Idempotency-Key: payment-100
Order: A
Amount: 15,000

→ APPROVED

동일 Key + 동일 Request 재전송

→ 기존 APPROVED 결과 반환
```

이를 통해 응답 유실이나 클라이언트 재시도로 동일 요청이 반복되더라도 동일한 비즈니스 효과가 다시 발생하지 않도록 한다.

---

## BR-03. 같은 멱등성 키에 다른 요청 내용이 들어오면 거부한다

하나의 `Idempotency-Key`는 하나의 논리적 요청에만 대응해야 한다.

따라서 기존 요청과 동일한 멱등성 키를 사용하면서 요청 내용이 다른 경우 이를 기존 요청의 재시도나 새로운 결제로 처리하지 않는다.

```text
첫 번째 요청

Idempotency-Key: payment-100
Order: A
Amount: 15,000


두 번째 요청

Idempotency-Key: payment-100
Order: B
Amount: 20,000
```

두 번째 요청은 충돌로 판단하여 거부하고 기존 요청의 처리 결과는 변경하지 않는다.

---

## BR-04. 승인 결과를 알 수 없는 결제는 즉시 실패로 확정하지 않는다

StoreFlow가 외부 결제 시스템에 승인 요청을 전달한 이후 응답을 받지 못했다고 해서 실제 결제가 실패했다고 단정할 수 없다.

```text
StoreFlow
    │
    │ 승인 요청
    ▼
Payment System
    │
    │ 승인 처리
    X
응답 유실
```

외부 결제 시스템에서는 이미 승인이 완료되었을 가능성이 있기 때문이다.

따라서 실제 승인 여부를 확인할 수 없는 결제는 성공 또는 실패로 임의 확정하지 않고 후속 확인이 필요한 대상으로 관리한다.

구체적인 상태 표현과 복구 방식은 이후 도메인 모델링 및 설계 과정에서 결정한다.

---

## BR-05. 취소된 결제는 다시 취소할 수 없다

이미 취소가 완료된 결제에 동일한 취소 효과가 다시 발생해서는 안 된다.

```text
Payment
→ APPROVED
→ CANCELED

동일 Payment
→ 취소 재요청

추가 취소 X
```

응답 유실이나 요청 재전송이 발생하더라도 동일한 결제가 여러 번 취소되어서는 안 된다.

취소 및 부분 취소에 대한 상세 정책은 해당 기능을 구현하는 시점에 확장하여 정의한다.

---

# 2. 정상·예외 사용자 시나리오

## 2.1 정상 사용자 시나리오

### N-01. 정상 주문 및 결제

사용자가 POS에서 주문을 생성하고 해당 주문에 대한 결제를 수행한다.

```text
1. POS가 주문을 생성한다.
2. StoreFlow가 주문을 저장한다.
3. POS가 해당 주문에 대한 결제를 요청한다.
4. StoreFlow가 외부 결제 시스템에 승인을 요청한다.
5. 외부 결제 시스템이 결제를 승인한다.
6. StoreFlow가 승인 결과를 반영한다.
7. POS가 결제 성공 결과를 전달받는다.
```

### 기대 결과

* 주문이 정상적으로 생성된다.
* 해당 주문에 대한 결제가 수행된다.
* 승인된 결제 결과가 저장된다.
* POS는 결제 성공 결과를 전달받는다.

---

### N-02. 완료된 동일 요청의 재전송

결제가 이미 정상적으로 완료된 이후 POS가 동일한 멱등성 키와 동일한 요청을 다시 전송한다.

```text
첫 번째 요청
→ 결제 승인
→ 결과 저장

동일 요청 재전송
→ 기존 요청 확인
→ 기존 결과 반환
```

### 기대 결과

* 새로운 결제를 생성하지 않는다.
* 외부 결제 승인을 다시 수행하지 않는다.
* 기존 결제 결과를 반환한다.

관련 규칙:

* `BR-01`
* `BR-02`

---

## 2.2 예외 사용자 시나리오

### E-01. 결제가 완료된 주문에 새로운 결제 요청

이미 결제가 완료된 주문에 대해 새로운 결제 요청이 전달된다.

```text
Order A
→ Payment APPROVED

Order A
→ 새로운 결제 요청
```

### 기대 결과

* 새로운 결제 승인을 수행하지 않는다.
* 기존 결제 결과를 변경하지 않는다.

관련 규칙:

* `BR-01`

---

### E-02. 동일 멱등성 키와 동일 요청 재전송

POS가 기존 요청과 동일한 `Idempotency-Key`와 동일한 요청 내용을 다시 전송한다.

```text
Idempotency-Key: payment-100
Order: A
Amount: 15,000

→ 처리 완료

Idempotency-Key: payment-100
Order: A
Amount: 15,000
```

### 기대 결과

* 새로운 비즈니스 작업을 생성하지 않는다.
* 외부 결제를 다시 수행하지 않는다.
* 기존 처리 결과를 반환한다.

관련 규칙:

* `BR-02`

---

### E-03. 동일 멱등성 키에 다른 요청 전달

첫 번째 요청:

```text
Idempotency-Key: payment-100
Order: A
Amount: 15,000
```

두 번째 요청:

```text
Idempotency-Key: payment-100
Order: B
Amount: 20,000
```

### 기대 결과

* 두 번째 요청을 거부한다.
* 새로운 결제를 수행하지 않는다.
* 기존 요청의 결과를 변경하지 않는다.

관련 규칙:

* `BR-03`

---

### E-04. 외부 결제 승인 결과를 확인할 수 없는 경우

StoreFlow가 외부 결제 시스템에 승인 요청을 전달했지만 정상적인 응답을 받지 못한다.

```text
StoreFlow
    │
    │ 승인 요청
    ▼
Payment System
    │
    X 응답 유실
```

이 시점에서 StoreFlow는 실제 결제가 승인되었는지 거절되었는지 확정할 수 없다.

### 기대 결과

* 즉시 결제 실패로 확정하지 않는다.
* 임의로 결제 성공으로 확정하지 않는다.
* 동일한 결제를 새로운 승인 요청으로 즉시 다시 처리하지 않는다.
* 실제 승인 결과를 확인할 수 있도록 후속 처리 대상으로 관리한다.

관련 규칙:

* `BR-04`

---

### E-05. 취소된 결제에 다시 취소 요청

이미 취소가 완료된 결제에 대해 취소 요청이 다시 전달된다.

```text
Payment
→ APPROVED
→ CANCELED

동일 Payment
→ Cancel 요청
```

### 기대 결과

* 새로운 취소 효과가 발생하지 않는다.
* 기존 취소 결과가 변경되지 않는다.

관련 규칙:

* `BR-05`

---

# 3. 주요 불변식 목록

비즈니스 규칙과 사용자 시나리오를 기준으로 StoreFlow가 반드시 지켜야 하는 주요 불변식을 정의한다.

## INV-01. 결제 완료 주문의 중복 결제 금지

> 결제가 완료된 주문에 새로운 결제 승인 효과가 발생해서는 안 된다.

결과 전달 실패나 사용자의 재시도로 새로운 요청이 발생하더라도 하나의 완료된 주문이 중복 결제되어서는 안 된다.

관련 규칙:

* `BR-01`

---

## INV-02. 동일 논리 요청의 멱등성

> 동일한 멱등성 키와 동일한 요청은 하나의 논리적 요청으로 취급해야 한다.

동일 요청이 여러 번 전달되더라도 새로운 비즈니스 효과가 발생해서는 안 된다.

```text
동일 Key
+
동일 Request

→ 동일한 논리적 요청
→ 동일한 처리 결과
```

관련 규칙:

* `BR-02`

---

## INV-03. 멱등성 키와 요청 내용의 일관성

> 하나의 멱등성 키는 하나의 요청 내용에만 대응해야 한다.

동일한 키에 서로 다른 요청이 전달된 경우 기존 요청의 재시도나 새로운 결제로 처리해서는 안 된다.

```text
동일 Key
+
다른 Request

→ 요청 거부
```

관련 규칙:

* `BR-03`

---

## INV-04. 불확실한 결제 결과의 임의 확정 금지

> 실제 승인 결과를 확인할 수 없는 결제를 성공 또는 실패로 임의 확정해서는 안 된다.

승인 요청 이후 정상적인 응답을 받지 못했다는 사실만으로 실제 결제가 실패했다고 판단할 수 없다.

```text
승인 요청 전달
+
승인 결과 확인 불가

≠ APPROVED
≠ FAILED
```

관련 규칙:

* `BR-04`

---

## INV-05. 중복 취소 금지

> 이미 취소된 결제에 동일한 취소 효과가 다시 발생해서는 안 된다.

취소 결과 전달 실패나 요청 재전송이 발생하더라도 하나의 취소가 여러 번 반영되어서는 안 된다.

관련 규칙:

* `BR-05`

---

# 정리

현재 단계에서 정의한 비즈니스 규칙과 불변식의 관계는 다음과 같다.

| 비즈니스 규칙                                    | 주요 불변식                        |
| ------------------------------------------ | ----------------------------- |
| `BR-01` 결제 완료된 주문은 다시 결제할 수 없다.            | `INV-01` 결제 완료 주문의 중복 결제 금지   |
| `BR-02` 같은 멱등성 키와 같은 요청은 같은 결과를 반환한다.      | `INV-02` 동일 논리 요청의 멱등성        |
| `BR-03` 같은 멱등성 키에 다른 요청은 거부한다.             | `INV-03` 멱등성 키와 요청 내용의 일관성    |
| `BR-04` 승인 결과를 알 수 없는 결제는 즉시 실패로 확정하지 않는다. | `INV-04` 불확실한 결제 결과의 임의 확정 금지 |
| `BR-05` 취소된 결제는 다시 취소할 수 없다.               | `INV-05` 중복 취소 금지             |

이 문서에서는 **무엇을 지켜야 하는가**까지만 정의한다.

이를 어떤 `Order`, `Payment`, 상태와 객체로 표현할지는 `03-domain-model.md`에서 다루고, 멱등성 저장 방식이나 동시성 제어와 같은 구체적인 구현 방법은 이후 실험과 ADR에서 결정한다.
